### C2. Observed drift vs operator host (numeric)

Method: SSH round-trip with host timestamps bounding the device reading (device BusyBox date
lacks %3N, so whole-second epoch comparison with SSH-latency bounds; host is NTP-synced —
`timedatectl NTPSynchronized=yes`).

```
sample1: host_t0=1789437776.470  device=1789437765  host_t1=1789437776.684  → device − host ≈ −11.2 s
sample2: host_t0=1789437776.690  device=1789437766  host_t1=1789437776.902  → device − host ≈ −11.1 s
sample3: host_t0=1789437776.908  device=1789437766  host_t1=1789437777.131  → device − host ≈ −11.0 s
```

**Observed drift: ≈ −11 seconds (device behind the NTP-synced operator host).**
SSH round-trip ≈ 0.2 s, so the −11 s figure is real drift, not measurement noise.
Cross-check: device `date -u` 02:02:11 vs host `date -u` 02:02:22 at the same moment —
consistent −11 s.

### C4. GO / NO-GO on the clock

**NO-GO.**

Reasons (all three must hold before recipes proceed; none currently does):

1. **Drift is already −11 s and growing.** sysntpd is running and enabled but has zero NTP
   servers reachable (upstream gateway dead, DNS dead). The device has no RTC on this platform
   family; after any reboot the clock will reset to the firmware epoch and be far worse than
   −11 s. All TLS-dependent recipe steps (blossom.primal.net artifact fetch, apk index fetch)
   would fail cert validation.
2. **Wrong device.** Even with a perfect clock, recipes for issue #32 target the CF-WR632AX
   (25.12.4); this device is a GL-MT6000 (24.10.1, opkg not apk). No recipe may run here
   regardless of clock.
3. **Required before proceeding (exact list):**
   - Restore upstream connectivity on the test device (bring up the WAN gateway / a WiFi STA
     uplink that actually carries traffic), so `ping -c 3 8.8.8.8` returns 0% loss.
   - Let sysntpd step the clock (`logread | grep -i ntp` must show sync lines), or manually
     push `date -s @<epoch>` from the operator host and re-measure.
   - Re-run the drift measurement: **GO threshold = |delta| ≤ 5 s** vs the NTP-synced host
     (per the clock-gate pattern in the physical-router-testing skill).
   - AND: confirm the device under test is actually the CF-WR632AX (MAC OUI 40:A5:EF,
     board_name `comfast,cf-wr632ax`, /proc/mtd shows SPI-NAND partitions, OpenWrt 25.12.4,
     apk present). If the intended target is this MT6000, that is a different task and needs
     an explicit operator decision — the issue-32 recipes do not apply to it.

Until then: **recipes must NOT proceed with the current clock, and must not proceed on this
device at all.**
